# 任务划分与分块计算

我们已经知道一行输出怎样计算。现在把这些工作交给多个线程。

## 1. 先确定输出由谁写

对于不同的 i，程序更新的是 C 的不同输出行。因此可以让一个线程负责一整行，而所有线程共同读取 A、B。

在这一划分下，不同线程不会同时累加同一个 `C[i,j]`。如果改为按单个非零元素分工，同一行的多个非零元素可能由不同线程处理，它们会写同一个输出位置，就需要额外处理同步或归并。

!!! note "并行循环的第一步"
    先找到每个任务读哪些数据、写哪些数据，再判断任务之间能否独立执行。只给循环加上 `parallel for`，不能自动解决共享写入问题。

## 2. 按行静态分配

可以用下面的简化结构表达按行并行：

```cpp
#pragma omp parallel for schedule(static)
for (size_t i = 0; i < M; ++i) {
    // 计算 C 的第 i 行
}
```

`parallel for` 建立并行区域并分配循环迭代。`schedule(static)` 在开始时分配工作；这里没有指定 chunk，线程通常得到相近数量的连续行。

当每行的非零数相近时，行数可以近似代表工作量。但 `skewed` 将较多非零元素集中在前约 1/8 行：某个连续行段就可能比其他行段重得多。

## 3. 动态领取行

`schedule(dynamic, 1)` 将一行作为一次领取的任务。线程完成当前行后继续领取下一行，直到所有行被处理。

这样不必在开始时预测每个线程的总工作量，但领取任务本身也有开销。如果任务数量很多、每个任务很轻，就需要关注这一开销。

实际源码通过 `schedule(runtime)` 使用运行参数设置的调度方式。先在 `src/main.cpp` 找到 `schedule` 与 `chunk` 的参数解析，再看 `src/benchmark.cpp` 中将它们传给 `omp_set_schedule` 的位置，最后回到 `src/spmm_parallel.cpp` 中的 `schedule(runtime)` 循环。

## 4. 按非零数构造行块

另一种办法是在运行前，根据 CSR 的 `row_ptr` 构造若干连续行块，尽量让每块的非零数接近 `--block-nnz`。

它仍然让完整输出行由同一个任务负责，同时把任务大小的依据从“行数”改为“非零数”。单行不会拆开，所以一个很重的行仍可能超过目标值。

打开 `src/partition.cpp`，观察：什么时候结束当前块？遇到超过目标非零数的一行时怎样处理？然后在 `src/spmm_parallel.cpp` 中找到这些块怎样进入并行循环。

## 5. 输出列也可以分块

Tiled 实现把任务进一步划分为：

```text
连续行块 × 一段输出列
```

每个任务更新 C 中独立的矩形区域。在一段列内部，内核使用局部数组保存部分和，遍历该行非零元素后再写入 C。实际实现包含 32 列微块和尾部处理，列循环使用 `omp simd`。

`omp simd` 表达循环可以采用 SIMD 执行。它与启动 OpenMP 线程是两种不同层次的并行，最终指令仍由编译器和目标 CPU 决定。

!!! tip "分块尺寸影响多件事情"
    分块会改变任务数量、局部工作集，以及非零数组被重复访问的次数。不要只根据“块越小”或“块越大”判断性能。固定输入与线程数，逐组测量。

打开 `src/spmm_tiled.cpp`：先找到行块、列块两层循环的 `collapse(2)`，再找到微块中的局部 `sums`。把这些位置与“任务区域”和“部分和”对应起来。

## 6. 动手试一试

先按照[操作步骤](run.md)完成构建和快速验证，再执行完整测量。随后从以下方向选择一个进行比较，命令都在 Lab1 中执行。

### 观察分工

在 `raw.csv` 中筛选 `record=thread`。固定 profile、实现和线程数，比较各线程的 `updates`、`compute_s` 与 `wait_s`。先看实际工作量是否相近，再看哪些线程先完成、哪些线程仍在计算。

比较 `uniform` 与 `skewed` 时，固定维度和总非零数。再比较 Rows、Dynamic 和 NNZ blocks，观察改变任务分配后，线程统计怎样变化。

### 改变行块

```bash
for block in 64 256 1024; do
  python3 run.py --block-nnz "$block" --output "results/block_$block"
done
```

这些数值是每个行块的**目标非零数**，不是行数。记录构造出的任务数量，以及当前配置中各线程的工作量。

### 改变列块

```bash
for tile in 32 64 128 256; do
  python3 run.py --tile "$tile" --output "results/tile_$tile"
done
```

固定线程数和输入，比较 Tiled 的耗时与 `nnz_visits`。如果时间改变，尝试把它与任务数量、部分和存储和重复访问联系起来。

??? info "看到 wait_s 就能认定负载不均衡吗？"
    这里的 `wait_s` 记录线程结束本阶段后在屏障处的等待。等待可能受到工作量、调度或操作系统活动影响。应同时查看 `updates`、`compute_s` 和多次测量，不能只靠一个等待数值判断原因。
