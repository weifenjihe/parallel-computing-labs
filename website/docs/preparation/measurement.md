# 怎样测量程序

程序跑完后，我们通常想知道“这个版本是否更快”。要回答这个问题，先确定比较的是同一项工作，再看耗时和相关统计。

## 一次只改变一个条件

比较两个实现时，固定输入规模、数据分布、随机种子和线程数。例如，比较 Lab2 的按行转置与分块转置，应使用相同的 N 和线程数。

如果要研究线程数，就固定实现和分块尺寸；如果要研究分块，就固定线程数。把每次的命令和输出目录记下来，以后才能准确找到对应数据。

!!! tip "结果取决于你的运行环境"
    CPU、内存、编译器以及后台程序都会影响时间。请记录自己的环境，并在同一台电脑上完成一组比较。运行时尽量保持电源状态一致，避免同时执行其他耗时任务。

## 先验证，再测量

每个实验都支持 `--verify`。先运行操作页的小规模验证：Lab1 与 Lab4 逐元素对比串行稀疏乘法参考，Lab2 检查转置坐标，Lab3 逐桶对比串行计数，Lab5 对比软件整数矩阵乘法。验证发生在核心计时之外，失败会指出位置并停止。

浮点结果允许 `1e-10 + 1e-9 × |参考值|` 的绝对误差，整数结果要求完全相同。修改 C++ 或 RTL 后，重新构建并验证，再运行正式测量；验证会影响运行间的数据访问，因此正式性能比较建议在单独的小规模验证后运行。

```text
VERIFY PASS: ...           → 当前输出通过完整比较
VERIFY FAIL at (...) ...   → 查看错误坐标、期望值与实际值
```

## 为什么会运行多次？

一次时间可能受到操作系统调度、缓存状态和后台活动影响。Lab1～Lab4 默认先预热，再重复测量，并用中位数汇总。`raw.csv` 保存逐次记录，`summary.csv` 保存整理后的数据。

中位数可以减轻个别异常值的影响，但不能消除系统持续受到的干扰。如果多次时间波动很大，先查看原始记录和运行环境，再解释实现之间的差别。

Lab5 默认每个配置仿真一次。它主要比较硬件周期；增加 `--repeat` 后，会按文档改变握手停顿的种子，并选取中位周期对应的记录。

## 加速比的分母是谁？

加速比定义为：

```text
加速比 = 基准配置的时间 / 当前配置的时间
```

例如，在一个说明公式的假设中，基准用时 120 ms，当前配置用时 60 ms，加速比就是 2。这只是公式示例，请使用自己测量的数值。

| 比较目的 | 应固定什么？ | 基准配置 |
|---|---|---|
| 比较不同实现 | 输入和线程数／进程数等实验条件 | 文档指定的串行实现 |
| 研究线程扩展 | 输入、实现、分块 | 同一实现的单线程版本 |
| 研究 MPI 进程扩展 | 输入、实现、分块、划分方式 | 同一实现的单进程版本 |
| 研究双缓冲 | 输入、阵列、三维分块、DRAM 参数 | 相同条件的单缓冲配置 |
| 研究阵列大小 | 输入、三维分块、缓冲、DRAM 参数 | 相同条件的最小阵列配置 |

Lab1 的 `speedup` 与 `thread_speedup` 使用不同的基准；Lab4 的 `speedup` 与 `process_speedup` 也一样。Lab5 的 `speedup` 以 `baseline_*` 字段记录的配置为准。阅读数值时，请同时查看这些条件。

## 计时范围也需要看

Lab1～Lab3 的核心测量包含并行计算及相关调度和同步；输入生成等准备工作在计时之外。Lab4 的计时还包含 B 数据打包和通信，但交换计划准备和最终 checksum 汇总在计时之外。具体范围列在各实验操作页。

Lab5 的 `cycles` 是仿真电路完成任务所用的周期，`host_seconds` 是电脑驱动仿真花的时间。两者回答不同的问题。比较加速器设计时，使用周期、传输字节数和有效乘加次数；估计自己需要等待多久时，可以看宿主机时间。

## 从哪个文件开始看？

先打开 `summary.csv`，确认当前行的规模、实现、并行度和分块参数，再看汇总时间或周期。需要观察各线程或各进程时，回到 `raw.csv`，按 `record` 区分记录类型。

CSV 可以用文本编辑器、表格软件或 Python 阅读。整数统计通常描述“完成了多少工作”，时间描述“完成这些工作花了多久”。先把这两类信息对应起来，再讨论等待、通信或访存。

??? info "checksum 能说明什么？"
    `checksum` 是输出元素的总和。它便于发现明显的异常，也能帮助核对同一组输入的运行记录。不同错误可能得到相同总和，因此单个 checksum 不能证明完整结果正确。

    阅读实现时仍应检查每个输出由谁更新、是否遗漏元素，以及共享更新是否正确同步。

## 保存一组实验结论

用一张表记录“实现、规模、并行度、分块、时间或周期、验证是否通过”。随后写清三个问题：改变了什么条件，数据出现了什么变化，哪些代码与统计支持你的解释。只观察到等待或加速比变化时，先保留原始记录，避免把单次波动当作结论。

完整扫描可能持续数分钟甚至更久。进度中的 `i/total` 是程序启动次数，每次还会执行预热与多次测量。中断后 `raw.csv` 只包含已完成配置；最终 `summary.csv` 和图表需要全部扫描完成。重新运行使用新的输出目录，不自动从部分记录续跑。
